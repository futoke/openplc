# Лабораторная работа: управление резервуаром на OpenPLC

## 1. Цель и результат

Вы развернёте два контейнера на собственном компьютере Windows, создадите проект ПЛК, свяжете его с веб-интерфейсом по Modbus TCP и дополните программу ST счётчиком включений насоса. Предполагается знакомство с командной строкой и Python; ST изучается по ходу работы. Python отдельно в Windows не устанавливается.

Результат: свой проект OpenPLC, изменённое тело ST и отчёт по [шаблону](REPORT-TEMPLATE.md). Контрольных вопросов нет; понимание подтверждается объяснением собственного алгоритма и протоколом испытаний.

## 2. Как устроен стенд

```text
Windows
  OpenPLC Editor ── HTTPS, localhost:8443 ──> контейнер openplc
  Браузер ───────── HTTP, localhost:8080 ───> контейнер hmi
                                               │
                         Modbus TCP openplc:502│
                                               ▼
                                         контейнер openplc
```

Редактор нужен для написания, сборки, загрузки и отладки. Runtime выполняет программу циклически. HMI (Human–Machine Interface) — интерфейс оператора; в этой лабораторной его Python-процесс также моделирует резервуар. Браузер не исполняет ST.

Замкнутый цикл: PLC выдаёт `Pump` → Python рассчитывает изменение уровня → Python записывает `LowLevel` и `HighLevel` → PLC принимает следующее решение. Никакое физическое оборудование не требуется.

В контейнере HMI находятся Python 3.12, Flask 3.1.1 и PyModbus 3.8.6. Flask обслуживает страницу и API, PyModbus читает и записывает биты PLC. В исходном коде задан бак высотой 1 м и площадью 0,1 м², то есть объёмом 100 л. Приток насоса уменьшается при росте уровня; слив через отверстие существует и при включённом насосе. Используется баланс `dh/dt = (Qвход − Qвыход) / S` с небольшими шагами интегрирования. Поэтому скорость изменения уровня непостоянна.

Датчики TRUE означают, что вода достигла соответствующей отметки: нижней 25% или верхней 90%. Состояние `HighLevel=TRUE`, `LowLevel=FALSE` считается противоречивым.

## 3. Docker: необходимая теория

**Образ (image)** — набор файлов и настроек для запуска приложения. Образ Runtime скачивается из реестра `ghcr.io`, а образ HMI собирается по `hmi/Dockerfile`. **Контейнер (container)** — запущенный экземпляр образа со своим окружением и файловой системой. Можно пересоздать контейнер из того же образа. [Образы](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/), [контейнеры](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/).

Контейнеры разделяют ядро ОС, в отличие от отдельных полноценных виртуальных машин. Наши образы Linux, поэтому в Windows Docker Desktop использует Linux-среду WSL 2. Приложение Docker Desktop управляет окружением, Docker Engine запускает контейнеры, а CLI `docker` отправляет ему команды. Наличие одной команды `docker` ещё не означает, что Engine работает.

**Dockerfile** описывает сборку образа HMI: `FROM python:3.12-slim` задаёт основу, `WORKDIR` — рабочую папку, `COPY` переносит файлы, `RUN pip install` ставит зависимости внутрь образа, `CMD` запускает приложение. **Compose** описывает несколько сервисов, их порты, окружение и хранилища в YAML. Одна команда поднимает весь стенд. [Docker Compose](https://docs.docker.com/compose/).

В [docker-compose.yml](../docker-compose.yml):

| Настройка | Что она означает в этом стенде |
|---|---|
| `image` у openplc | Готовый образ Runtime |
| `build: ./hmi` | Сборка HMI из локальной папки |
| `ports` | Публикация портов контейнера в Windows |
| `PLC_HOST: openplc` | Имя сервиса PLC во внутренней сети |
| `depends_on` | Порядок старта; не гарантия готовности Modbus |
| `restart: unless-stopped` | Политика перезапуска контейнеров |
| `volumes` | Сохранение данных Runtime отдельно от контейнера |
| `cap_add` | Дополнительные Linux-возможности Runtime для управления ресурсами и приоритетом |

В записи `127.0.0.1:8080:8080` первое число порта относится к Windows, второе — к контейнеру; `127.0.0.1` ограничивает доступ этим компьютером. Внутри контейнера `localhost` указывает на него самого. Поэтому HMI использует имя `openplc`, а не `127.0.0.1`. Сервисы Compose находят друг друга по именам в общей сети. Публиковать Modbus 502 в Windows для этой схемы не требуется. [Сеть Compose](https://docs.docker.com/compose/how-tos/networking/).

Именованный том `openplc-data` сохраняет файлы Runtime при пересоздании контейнера. В обычной конфигурации его реальное имя включает префикс каталога проекта. Исходники вашего проекта всё равно храните отдельно в Windows. Не меняйте имя папки стенда посреди работы: Compose может создать другой проект и другой том. HMI хранит уровень только в оперативной памяти и после перезапуска начинает с 10%. [Хранилища Docker](https://docs.docker.com/engine/storage/volumes/).

## 4. Подготовка Windows и установка Docker

### 4.1. Проверка компьютера

Нужны 64-разрядная Windows, аппаратная виртуализация, интернет для загрузки образов и возможность выполнить настройку WSL от администратора. Методика рассчитана на обычные x64-компьютеры.

Выполните `winver` и запишите редакцию, версию и сборку Windows. В «Диспетчер задач → Производительность → ЦП» проверьте «Виртуализация: включено». Если отключено, включите Intel VT-x / AMD-V в UEFI/BIOS по инструкции изготовителя компьютера.

На момент подготовки Docker указывает WSL не ниже 2.1.5 и минимум 8 ГБ RAM. Перед установкой сопоставьте свою ОС с [официальными требованиями Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/). Для Windows 10 это особенно важно: поддержка зависит не только от наличия 22H2, но и от срока обслуживания конкретной редакции.

### 4.2. WSL 2

Откройте PowerShell от имени администратора:

```powershell
wsl --install
```

Перезагрузите компьютер, если это предложено. При первом запуске установленного дистрибутива создайте имя пользователя и пароль Linux. Затем выполните:

```powershell
wsl --update
wsl --set-default-version 2
wsl --status
wsl --version
wsl --list --verbose
```

В последней таблице у установленного дистрибутива должна быть версия 2. Если он уже существовал с версией 1, преобразуйте его командой `wsl --set-version Ubuntu 2`, подставив точное имя из таблицы. Версия пакета WSL из `wsl --version` и номер архитектуры WSL 1/2 — разные показатели.

Если `wsl --install` только показывает справку, используйте `wsl --list --online`, затем `wsl --install -d Ubuntu`. Для старых сборок Windows сначала установите обновления. Подробности и варианты ошибок: [установка WSL от Microsoft](https://learn.microsoft.com/en-us/windows/wsl/install).

### 4.3. Docker Desktop

1. Скачайте установщик Windows x86_64 с [официальной страницы Docker](https://docs.docker.com/desktop/setup/install/windows-install/).
2. Запустите `Docker Desktop Installer.exe`, выберите WSL 2, если мастер предлагает выбор backend. Завершите установку и требуемую перезагрузку.
3. Запустите Docker Desktop из меню «Пуск», ознакомьтесь с условиями и завершите первоначальную настройку.
4. В Settings → General проверьте использование WSL 2 engine, если этот переключатель доступен в вашей версии. Используйте режим **Linux containers**. Если меню предлагает «Switch to Linux containers», выполните переключение.
5. Дождитесь состояния работающего Engine. Откройте новое окно PowerShell и проверьте:

```powershell
docker version
docker compose version
docker info --format '{{.OSType}}'
docker run --rm hello-world
```

Ожидаются разделы Client и Server, версия Compose, значение `linux` и приветствие `hello-world`. Контейнер проверки автоматически удаляется после выполнения. Отдельно устанавливать Compose или Python не требуется.

## 5. Подготовка файлов и запуск контейнеров

Скопируйте материалы из репозитория, например в `C:\OpenPLC-Lab`. Внутри должны находиться `docker-compose.yml`, папка `hmi` и файл `PLC-ST.txt`. Сохраните эту структуру. Установщик OpenPLC Editor в репозиторий не входит: скачайте **Windows x64 EXE** со страницы [официального релиза OpenPLC Editor v4.3.2](https://github.com/Autonomy-Logic/openplc-editor/releases/tag/v4.3.2). Проект редактора далее создавайте в отдельной папке, например `C:\OpenPLC-Projects\TankLab`.

Команды ниже выполняются в обычном PowerShell Windows, не в терминале Linux:

```powershell
Set-Location 'C:\OpenPLC-Lab'
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail 80 openplc hmi
```

Путь замените своим. `config --quiet` проверяет YAML и при успехе ничего не печатает. `up` создаёт сеть, том и контейнеры; `--build` собирает HMI, `-d` оставляет сервисы в фоне. При первом запуске загрузка может занять несколько минут. В `ps` оба сервиса должны быть запущены (`Up`); при ошибке изучите журналы.

Откройте <http://localhost:8080>. Страница должна загрузиться, но `PLC OFFLINE` до загрузки проекта с Modbus-сервером ожидаем. Это ещё не ошибка HMI.

## 6. Установка OpenPLC Editor

1. Запустите скачанный установщик OpenPLC Editor 4.3.2 для Windows x64 двойным щелчком. Следуйте мастеру: выбор пользователя/каталога, установка и завершение — если эти страницы предлагаются вашей сборкой.
2. Откройте OpenPLC Editor через меню «Пуск» или созданный ярлык.

Python и зависимости редактора вручную устанавливать не нужно. Исходный код проекта: [официальный репозиторий OpenPLC Editor](https://github.com/Autonomy-Logic/openplc-editor). В этой работе используйте версию 4.3.2; интерфейс других версий может отличаться.

## 7. Создание исходного проекта

Названия разделов ниже приведены по их назначению и англоязычным подписям; расположение кнопок может отличаться между сборками. Каталог `test` служит справочным примером конфигурации, но для сдачи нужен собственный проект.

### 7.1. POU и переменные

1. Создайте новый PLC project, задайте имя `TankLab` и сохраните в отдельной папке.
2. Добавьте POU через кнопку добавления в дереве проекта: имя `TankControl`, тип `Program`, язык `ST`.
3. Откройте [PLC-ST.txt](../PLC-ST.txt) в текстовом редакторе с UTF-8. В таблице Variables создайте все девять переменных по верхней таблице файла. Class — Local; Location задайте точно; у FillTimer тип TON, Location и Initial пустые.
4. Скопируйте в область тела программы **только текст между `=== BEGIN BODY ===` и `=== END BODY ===`**. Сами маркеры не копируйте. Не добавляйте туда `PROGRAM`, `VAR`, `END_VAR`, `END_PROGRAM`: оболочку создаёт редактор.
5. Сохраните проект. Прочитайте [справку ST](ST-QUICKSTART.md), затем проследите исходный алгоритм сверху вниз.

### 7.2. Устройство и циклическая задача

В конфигурации устройства выберите **OpenPLC Runtime v4**, IP `127.0.0.1`. Если есть отдельное поле порта, используйте `8443`. Это адрес управления из Windows, а не адрес Modbus HMI.

В Resource / Tasks создайте задачу `task0`: Triggering `Cyclic`, Interval `T#20ms`, Priority `1`. В Instances создайте `instance0`, выберите Program `TankControl` и Task `task0`. Без привязки экземпляра программа может собраться, но не исполняться.

### 7.3. Modbus TCP Server

Через добавление в дереве проекта создайте **Modbus TCP Server** и включите его (`Enabled`). Задайте:

| Параметр | Значение |
|---|---|
| Transport | TCP |
| Network interface | `0.0.0.0` |
| Port | `502` |
| Coils → QX bits | **16** |
| Coils → MX bits | **8** |

Остальные размеры можно оставить как в исходном примере: IX 8192, IW 1024, QW/MW/MD/ML по 1024. В работе используются только coils. Не путайте сервер Modbus с подключением PLC к чужому Modbus-серверу.

Coil — один доступный по протоколу бит. Здесь нумерация начинается с нуля. Первые 16 coils отображают QX, следующие 8 — MX:

| Переменная | Location | Coil | Кто записывает |
|---|---|---:|---|
| StartBtn | `%MX0.0` | 16 | HMI |
| StopBtn | `%MX0.1` | 17 | HMI |
| ResetBtn | `%MX0.2` | 18 | HMI |
| LowLevel | `%MX0.3` | 19 | Модель Python |
| HighLevel | `%MX0.4` | 20 | Модель Python |
| Pump | `%QX1.0` | 8 | ST |
| Alarm | `%QX1.1` | 9 | ST |
| AutoMode | `%QX1.2` | 10 | ST |

Если увеличить QX, например до 32, начало MX сместится, а HMI продолжит писать по старым адресам. Поэтому «не меньше 16» здесь недостаточно — нужно **ровно 16**. Сами команды и датчики не перезаписывайте присваиваниями в теле ST.

### 7.4. Сборка, загрузка, запуск

1. Убедитесь, что Docker Desktop и оба контейнера работают.
2. В редакторе выполните Build / Compile. Исправьте ошибки до успешного завершения сборки.
3. Подключитесь к Runtime `127.0.0.1` и выполните Upload / Build & Upload. При первом подключении к чистому Runtime создайте учётную запись через предложенный редактором диалог; при последующих используйте её. 
4. Дождитесь успешного окончания загрузки/компиляции на Runtime. Нажмите Play / Start и проверьте состояние Run.
5. Откройте HMI, дождитесь `PLC ONLINE`. Нажмите RESET, дождитесь отпускания команды, затем START.

Runtime v4 управляется редактором через HTTPS API на порту 8443; привычного веб-интерфейса Runtime v3 здесь нет. Адрес `http://localhost:8080` относится к нашему отдельному HMI. [Интеграция Editor и Runtime](https://github.com/Autonomy-Logic/openplc-runtime/blob/main/docs/EDITOR_INTEGRATION.md).

## 8. Проверка исходной программы

Откройте онлайн-наблюдение / отладку экземпляра `instance0` в редакторе. Наблюдайте `Pump`, `AutoMode`, `Alarm`, `LowLevel`, `HighLevel`, `FillTimer.Q` и, если доступно, `FillTimer.ET`. Кнопка HMI удерживает команду примерно 1 секунду; между нажатиями выжидайте не менее 2 секунд, не делайте быстрых двойных нажатий.

1. При уровне ниже 25% нажмите START: AutoMode и Pump становятся TRUE.
2. После прохождения 25% LowLevel становится TRUE, но насос продолжает работать: это гистерезис.
3. При 90% HighLevel становится TRUE, насос выключается. AutoMode остаётся TRUE.
4. Уровень снижается через слив. Ниже 25% насос включается снова без повторного START.
5. Во время наполнения нажмите STOP: AutoMode и Pump становятся FALSE. Слив продолжается. STOP не сливает воду мгновенно.
6. Нажмите START при уровне между 25% и 90%, когда насос выключен: включится AutoMode, но насос будет ждать снижения ниже 25%. Это штатное поведение.

Датчики, физика и страница обновляются реже цикла PLC (примерно 0,25 с и 0,5 с), поэтому в браузере допустим небольшой выход за порог и задержка индикации. `PLC ONLINE` означает успешный обмен, а не гарантирует состояние Run.

## 9. Самостоятельное задание: ограничение числа включений

Добавьте в ST контроль условного ресурса насоса. После **трёх включений** система должна требовать обслуживания, имитируемого кнопкой RESET. Меняются только переменные и тело `TankControl`; Python, физическая модель, адреса Modbus и HMI остаются прежними.

### 9.1. Точные требования

1. `StartCount` типа UINT начинается с 0 и увеличивается на 1 только при фактическом переходе итогового `Pump` FALSE → TRUE. Повторный START при уже работающем насосе не увеличивает счётчик. Автоматическое включение после опустошения тоже считается.
2. Разрешены три включения. При третьем включении насос продолжает наполнение. Когда он затем выключится (верхний датчик, STOP или авария), установите `ServiceRequired=TRUE`. Не обрывайте третье наполнение только из-за достижения счётчиком 3.
3. При ServiceRequired установите `Alarm=TRUE`, `AutoMode=FALSE`, `Pump=FALSE`. Четвёртое включение запрещено, START не снимает блокировку. Значение счётчика не растёт выше 3.
4. STOP выключает насос и автоматический режим, но не обнуляет счётчик. Остановка после третьего включения тоже активирует блокировку; «полное наполнение» для учёта включения не обязательно.

Добавьте локальные переменные без Location: `StartCount: UINT := 0`, `PrevPump: BOOL := FALSE`, `ServiceRequired: BOOL := FALSE`. При необходимости добавьте вспомогательные BOOL. Максимум включений равен 3; можно вынести его в отдельную переменную с начальным значением 3.

## 10. Обязательные испытания

Для каждой строки запишите условия, действия, ожидаемые и фактические значения, результат. Сохраняйте скриншоты HMI и окна наблюдения редактора. Во время испытаний не изменяйте физические параметры Python.

| № | Испытание | Ожидаемый результат |
|---|---|---|
| 1 | RESET при остановленном насосе, затем START ниже 25% | Count 0 → 1; Pump TRUE, ServiceRequired FALSE |
| 2 | Оставить насос включённым несколько секунд; снова нажать START | Count остаётся 1 |
| 3 | STOP после первого включения | Pump и AutoMode FALSE; Count остаётся 1 |
| 4 | Дождаться уровня ниже 25%, включить второй раз; дождаться 90%, затем естественного снижения и автоматического третьего включения | Count последовательно 2 и 3; гистерезис сохранён |
| 5 | Дождаться верхнего уровня на третьем включении | Count 3, ServiceRequired и Alarm TRUE, Pump и AutoMode FALSE |


## 11. Где находится Python и как его менять при необходимости

`hmi/app.py` содержит API, Modbus-клиент и расчёт воды; `hmi/templates/index.html` — интерфейс; `hmi/requirements.txt` — закреплённые версии библиотек; `hmi/Dockerfile` — рецепт окружения.

В API `GET /api/state` возвращает состояние, `POST /api/start`, `/api/stop`, `/api/reset` формируют импульсы команд. Фоновый поток читает Pump/Alarm/AutoMode и записывает датчики. Общий клиент защищён блокировкой, потому что им пользуются и HTTP-запросы, и поток модели.

Если потребуется изменить код, отредактируйте файл в Windows, сохраните UTF-8 и пересоберите только HMI:

```powershell
docker compose up -d --build hmi
docker compose logs --tail 60 hmi
docker compose exec hmi python --version
```

Исходники копируются в образ через COPY, а не подключены как общая папка. Поэтому один `docker compose restart hmi` не переносит изменения с диска. Установка пакетов через Windows `pip` тоже не меняет контейнер. Зависимости изменяют в requirements и включают повторной сборкой. Пересоздание HMI сбрасывает модель до 10%; обновите страницу после изменения HTML.

## 12. Остановка и типовые проблемы

Для завершения сеанса нажмите STOP в HMI, затем:

```powershell
docker compose stop
```

Для продолжения запустите Docker Desktop, выполните `docker compose start`, проверьте Run в редакторе и состояние HMI. `docker compose down` удаляет контейнеры и сеть, но по умолчанию сохраняет именованный том; флаг `-v` удаляет и том с данными. Для обычной работы используйте `stop`.

| Симптом | Проверка и действие |
|---|---|
| `docker` не найден | Завершите установку Desktop, откройте новое окно PowerShell |
| Есть Client, но нет Server; ошибка named pipe | Запустите Desktop и дождитесь Engine; проверьте WSL 2 и режим Linux |
| Ошибка виртуализации / WSL | Проверьте UEFI, обновления Windows, `wsl --status` и инструкцию Microsoft |
| `no configuration file provided` | Перейдите в папку с docker-compose.yml |
| Ошибка загрузки образа/пакетов | Проверьте интернет и настройки прокси Docker; сохраните текст ошибки |
| Имя `openplc` уже занято | Проверьте `docker ps -a`; используйте один экземпляр стенда, не удаляйте чужой контейнер |
| 8080 или 8443 занят | Проверьте `Get-NetTCPConnection -LocalPort 8080,8443 -ErrorAction SilentlyContinue`; выясните владельца порта |
| HMI не открывается | `docker compose ps`, `docker compose logs --tail 80 hmi`; адрес HTTP, не HTTPS |
| HMI показывает OFFLINE | Проверьте Run, добавление/включение Modbus, 0.0.0.0:502, QX=16, MX=8 и повторную загрузку |
| HMI ONLINE, START не действует | Проверьте Run, привязку task0, адрес StartBtn и Alarm; выше 25% остановленный насос ждёт снижения |
| Ошибка компиляции ST | Не вставлены ли маркеры/VAR в тело; совпадают ли имена, типы; есть ли END_IF и точки с запятой |
| После смены Runtime редактор отказывает в загрузке | Запишите обе версии, digest и текст ошибки; согласуйте совместимую пару с преподавателем |
| Изменения Python не появились | Пересоберите HMI с --build |
| Счётчик быстро растёт | Считаются циклы вместо переходов FALSE → TRUE |
| Счётчик всегда 0 или 1 | Проверьте переинициализацию и место обновления PrevPump |

Если меняете порт HMI, меняйте только левый порт, например `127.0.0.1:8081:8080`, и открывайте `http://localhost:8081`. Порт Runtime для этой работы лучше сохранить 8443, освободив его от другого своего стенда.
